# Codex Project Instructions

- New or changed obstacles must be visible, recognizable by name and correct sprite, selectable, placeable, and configurable in LevelEditor. Include footprint/size controls, erase/resize behavior and the requested Goals/PreLevel representation in the same task. Verify editor integration through code/asset checks; do not call a runtime-only change complete. The user performs manual editor/game tests. Do not control the user's computer or operate Unity/browser/native UI unless they explicitly request it. Do not create test levels or run builds, Play mode, or simulations without an explicit request; preserve the user's levels.

- For numbered level design, revisions, or design-reference feedback, read `Docs/LevelDesign/Memory.md` and `Docs/LevelDesign/Skills/tinyfixers-level-design/SKILL.md`, then resume from `Docs/LevelDesign/Design-State.md` before changing assets. Memory.md records the latest user rules and supersedes older conflicting design notes. Preserve user-approved levels; record explicit feedback separately from the agent's own visual assessment.

- Progressive content (split download) is the default for all NEW media. Every new or changed image, sound, video, VFX texture, material or large data must be planned with its download owner before it is added: (1) local only if it is needed in levels 1-50, the first session, main-menu chrome, or a small event/menu badge; (2) otherwise it belongs to its level pack (50-level block, via the level's ObstacleLibrary definition), its event pack, a mission/city pack, or a new pack. Do not add new `Resources.Load` string paths or scene/ScriptableObject references that silently pull remote-owned art into the player; route event art through the event config so `ProgressiveEventBuild` can strip it, and gate screens with `ProgressiveContent.GateEvent`. State the owner and estimated size in the delivery note. Rebuild and re-upload the content packs after changing any packaged asset (Docs/Backend/Parcali-Icerik-Yayin-Akisi.md).
- Do not run Unity builds, `dotnet build`, or other project build commands for this repository unless the user explicitly asks for a build in that turn.
- Remote level publishing: never create a release baseline until the user explicitly declares “bu ilk release” (or explicitly identifies a later app release). This is separate from permission to publish: upload only when the user explicitly asks to send/publish levels. Preparing tools, exporting previews or testing must not mark a release or deploy anything. Cloudflare management credentials stay on the developer machine and must never enter game assets or published content.
- Audio is centrally managed. All gameplay/obstacle SFX must use the existing central audio APIs (board sounds: `BoardAudioDirector.Emit` / `PlayOneShotClip`) and obey `GameSettings.SoundEnabled`; music obeys `GameSettings.MusicEnabled`. Do not bypass them with obstacle-local `AudioSource.Play` / `PlayOneShot` or a fallback source. Settings changes must immediately mute/unmute active sounds as well as gate new playback; use the central mixer/settings binding, unsubscribe setting events and cancel pending playback on disable/teardown. Reuse existing audio sources/pools rather than allocating sources per effect.
- Performance is a primary requirement. For gameplay/VFX changes, proactively review object churn, allocations, repeated board scans, and cleanup without waiting for a reminder. Reuse the existing pools for frequently spawned effects; prefer shared update loops and reusable buffers in hot paths. Verify reuse and cancellation/scene teardown behavior, and distinguish measured performance from expected improvements.
