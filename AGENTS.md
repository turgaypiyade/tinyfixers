# Codex Project Instructions

- For numbered level design, revisions, or design-reference feedback, read `Docs/LevelDesign/Skills/tinyfixers-level-design/SKILL.md` and resume from `Docs/LevelDesign/Design-State.md` before changing assets. Preserve user-approved levels; record explicit feedback separately from the agent's own visual assessment.

- Do not run Unity builds, `dotnet build`, or other project build commands for this repository unless the user explicitly asks for a build in that turn.
- Remote level publishing: never create a release baseline until the user explicitly declares “bu ilk release” (or explicitly identifies a later app release). This is separate from permission to publish: upload only when the user explicitly asks to send/publish levels. Preparing tools, exporting previews or testing must not mark a release or deploy anything. Cloudflare management credentials stay on the developer machine and must never enter game assets or published content.
- Audio is centrally managed. All gameplay/obstacle SFX must use the existing central audio APIs (board sounds: `BoardAudioDirector.Emit` / `PlayOneShotClip`) and obey `GameSettings.SoundEnabled`; music obeys `GameSettings.MusicEnabled`. Do not bypass them with obstacle-local `AudioSource.Play` / `PlayOneShot` or a fallback source. Settings changes must immediately mute/unmute active sounds as well as gate new playback; use the central mixer/settings binding, unsubscribe setting events and cancel pending playback on disable/teardown. Reuse existing audio sources/pools rather than allocating sources per effect.
- Performance is a primary requirement. For gameplay/VFX changes, proactively review object churn, allocations, repeated board scans, and cleanup without waiting for a reminder. Reuse the existing pools for frequently spawned effects; prefer shared update loops and reusable buffers in hot paths. Verify reuse and cancellation/scene teardown behavior, and distinguish measured performance from expected improvements.
